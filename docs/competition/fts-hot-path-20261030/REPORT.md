# 全文索引调优：词频与停用词优化收尾报告

## 实现与瓶颈依据

本补丁基于已提交版本 `965b5d35ec36218bffd2ece8442b2bf8038d4c9a`。该版本已有 IK 字符分类、仲裁、词典包装及 BENG 词元分配优化；本次新增两处分词热路径优化。

1. `ObAddWord::groupby_word` 原来对同一词元先查询再覆盖写回，重复计算哈希并加锁。改为 `set_or_update` 在同一次桶锁内插入或累加。保留首次计数为 1、后续累加传入词频、原排序规则及保留键的语义。
2. 停用词原来每次构造分配器、转换编码并查询带锁哈希集合。初始化时从同一停用词列表建立只读短 ASCII 整数索引，对 UTF-8 ASCII 词元用二分查找。保留大小写折叠、尾部 ASCII 空格语义；非 ASCII、其他字符集及超长词保留原路径。

这属于题目允许选择的“分词热路径”和“内存”优化，不要求把所有列举方向全部实现。没有修改测试数据、SQL、计时逻辑、评分脚本、固定基线或 CI 工作流。

题面提及的 `.github/workflows/vldb.yml` 在原提交和候选源码中均不存在，本次没有新增或改写 CI 工作流。以下为按原基准脚本完成的本地完整验证；GitHub 上传不等同于比赛平台已重新提测或 CI 已通过。

## 规定参数与性能结果

Ubuntu 20.04 / WSL2、Clang 17、`RelWithDebInfo`。两个服务端均为 `cpu_count=2`、`memory_limit=2G`，绑定 CPU `12,14`，客户端绑定 CPU `10`。使用专用端口 2901 和专用数据目录。没有调整其他任务或服务；同一 WSL 中存在其他任务，因此机器负载无法保证完全恒定。

独立性能实例的四轮顺序：原提交1 → 候选1 → 候选2 → 原提交2。该实例不穿插 SQL 回归，每轮使用新报告文件并重新导入、构建索引。参数：`ROWS=20000 BATCH=500 ROUNDS=3000 QUERY_ROUNDS=200 SAMPLES=3 WARMUP=30 SKIP_LOAD=0`。全部轮次保留，无剔除、无参数调整、无扣除 SELECT 1 耗时。原始文件以 `controlled-` 开头。

### 集成测试阶段的另外四轮

最初四轮在基准之间插入了 SQL 回归，不能排除实例状态和机器负载对耗时的影响。这组结果完整保留，单独记在 `integration-sequence-summary.json`：相对原提交的本机综合提升率为 **-169.70%**，固定基线参考原始分为 **{'submitted': [100.0, 100.0], 'candidate': [91.60045596879974, 84.82218794925136]}**。这组候选版存在明显退化，不能仅凭测试协议不同断言退化与代码无关。因协议不同，两组不混算，也不以较好的一组替换另一组。
